# N5Deal — схема данных и индексы

Шаг 2 · 5 октября 2026 · Основание: N5Deal-Scope-and-Acceptance.md, версия 1.0.

Повторное ревью: 6 октября 2026. Структура таблиц и индексов сохранена; уточнены SQL-проверки текста и границы гарантий.

Результат: 5 таблиц, 6 обычных составных индексов, 2 дополнительных уникальных ограничения и 5 первичных ключей. Модель предназначена для PostgreSQL и Prisma ORM 7. Это проект схемы; Docker, приложение, применение настоящих миграций и runtime seed относятся к шагу 3. Деплой остаётся последним этапом.

## Файлы

- `prisma/schema.prisma` — модели, enums, связи и индексы.
- `prisma/constraints.sql` — CHECK-ограничения и обязательность массивов для включения в первоначальную миграцию после CREATE TABLE.
- `prisma/seed-data.json` — подготовленные вымышленные fixtures, стабильные UUID и список demo-persona. Денежные значения — строки, даты — UTC ISO 8601. Это данные для будущего seed-скрипта, не исполняемый загрузчик.

## 1. Почему ровно пять таблиц

| Таблица | Ответственность | Почему отдельная |
| --- | --- | --- |
| `users` | Общая идентичность участника, роль, статус, имя, организация, страна | Одни и те же участники владеют активами, отправляют заявки и подвергаются модерации |
| `buyer_profiles` | Инвестиционный тезис, интересы, бюджет, публикация профиля | Эти поля нужны только Buyer; отсутствие профиля — реальное состояние onboarding |
| `assets` | Актив, его владелец, характеристики и публикация | Отдельный жизненный цикл и связь many-to-one с Seller |
| `inquiries` | Одно направленное обращение, адресат, необязательный актив, факт прочтения | Контакт должен сохраняться и быть доступен обоим участникам |
| `moderation_events` | История переходов статуса, причина и Manager | Одного текущего status недостаточно для нескольких блокировок/разблокировок и истории причин |

`moderation_events` — небольшое расширение, выбранное в шаге 1 ради объяснимой модерации. Исходное задание не требует полноценного audit subsystem. Общей таблицы событий, произвольного JSON payload и истории каждого изменения здесь нет.

Не нужны `seller_profiles`, `organizations`, `roles`, `permissions`, `sessions`, `accounts`, `countries`, `categories`, `licenses`, `currencies`, `conversations`, `messages`, `notifications`, `favorites`, `idempotency_requests`. Их сценарии отсутствуют или уже выражены текущими сущностями.

## 2. Связи и ключи

| Связь | Кардинальность | Реализация |
| --- | --- | --- |
| User → BuyerProfile | 1 → 0..1 | `BuyerProfile.userId` одновременно PK и FK; отдельный id и второй unique не нужны |
| User → Asset | 1 → 0..N | `Asset.sellerId` |
| User → Inquiry | 1 → 0..N в каждой из двух ролей | `senderId` и `recipientId` с именованными Prisma relations |
| Asset → Inquiry | 1 → 0..N | `assetId` nullable: Seller может обратиться к Buyer без конкретного актива |
| User → ModerationEvent | 1 → 0..N как автор или субъект | `managerId` и `targetUserId` |

Всего 7 внешних ключей. UUID используются для идентификаторов; Prisma `uuid()` генерирует их при создании через Prisma Client. В SQL, полученном из схемы, это не database-side default. Raw SQL и fixture loader должны передавать UUID самостоятельно. Идентификатор сам по себе не даёт права доступа.

Все FK используют `ON DELETE RESTRICT / ON UPDATE RESTRICT`. Пользователи логически удаляются через status, активы архивируются; случайное физическое удаление связанного пользователя или актива не должно стирать историю. `reset-demo` будет явной специальной операцией с зависимостями, а не обычным CRUD.

Система FK гарантирует существование пользователя, но не его роль. Условия «владелец — Seller», «профиль — Buyer», «автор модерации — Manager» проверяются use cases. Дублировать role в каждой дочерней таблице ради составных FK или писать триггеры для этого прототипа не требуется.

## 3. Устранённые дублирования

- У `BuyerProfile` нет второго id, `isPublished` или enum visibility: `publishedAt=null` означает DRAFT, дата означает PUBLISHED. При скрытии дата очищается, при новой публикации выставляется заново. Доменное название статуса вычисляется в DTO.
- У `ModerationEvent` нет поля action: переход в SUSPENDED — Suspend, в ACTIVE — Reactivate, в REMOVED — Remove. Сохраняются `fromStatus`, `toStatus`, причина и автор.
- У пользователя нет одновременно `status`, `isActive`, `isSuspended`, `deletedAt` и `suspendedAt`. Текущий статус — в User, время и причины переходов — в ModerationEvent.
- У заявки нет `isRead` и отдельного статуса доставки: достаточно `readAt`. `updatedAt` не нужен: текст и участники неизменяемы, единственное последующее изменение — readAt.
- В аудите нет `updatedAt`: события добавляются, не редактируются обычными use cases.
- Нет количества активов, сообщений, views или favourites в User/Asset: счётчики вычисляются, не синхронизируются вручную.
- Нет currency на каждой строке: по scope все суммы EUR. Если появится мультивалютность, это будет отдельное изменение модели и правил сравнения.
- Выбор лицензии None в UI сохраняется как `licenseType=null`; отдельный enum NONE не дублирует отсутствие значения. Other остаётся явным значением.
- Состояние бизнеса и публикация актива сохраняются раздельно: это разные факты. Трёхсостоянийный lifecycle Asset не сводится к одной дате.

`priceType` оставлен намеренно: у черновика цена ещё может быть не выбрана, FIXED может быть выбран без введённой суммы, ON_REQUEST — осознанный выбор. Одна nullable сумма не различает эти состояния.

## 4. Справочники и массивы интересов

Роли, статусы, категории, типы активов и небольшой список лицензий — PostgreSQL enums. Управление справочниками из админки не требуется. Страны — коды из фиксированного application-level allowlist; форма показывает человекочитаемые названия.

`targetCategories` — enum[], `targetJurisdictions` — varchar(2)[]. По ним нужны простые membership-фильтры, но нет дополнительных полей у связи. Поэтому отдельные `buyer_categories` и `buyer_countries` не добавлены. Это осознанное использование PostgreSQL-массивов, не заявление о полной нормализации many-to-many.

Сервер нормализует, проверяет и удаляет дубликаты из массивов. Пустой список стран означает любой рынок. Пустой список категорий допустим в черновике, но не при публикации. Не использовать JSON для полей, по которым фильтруется каталог.

БД исключает NULL-массивы, NULL-элементы и многомерные значения; действительность кодов стран и отсутствие дубликатов проверяет приложение. Если появятся редактируемые справочники, атрибуты связей или сложная аналитика, тогда оправданы таблицы связей.

## 5. Индексы: от запросов к схеме

Все шесть ниже — B-tree. `DESC` и последний уникальный ключ соответствуют стабильной сортировке. Индексы выбраны под постоянные пути чтения, а не под каждое поле формы. На 20 строках PostgreSQL вправе предпочесть sequential scan; это не ошибка и не основание отключать planner.

| Индекс | Поля в порядке индекса | Какой запрос обслуживает |
| --- | --- | --- |
| `assets_catalog_idx` | publicationStatus, publishedAt DESC, id DESC | Каталог: WHERE publicationStatus=PUBLISHED ORDER BY publishedAt DESC, id DESC LIMIT 12 |
| `assets_seller_idx` | sellerId, createdAt DESC, id DESC | Мои активы и активы участника у Manager: WHERE sellerId=? ORDER BY createdAt DESC, id DESC |
| `buyer_profiles_catalog_idx` | publishedAt DESC, userId DESC | Каталог Buyer: WHERE publishedAt IS NOT NULL ORDER BY publishedAt DESC, userId DESC |
| `inquiries_inbox_idx` | recipientId, createdAt DESC, id DESC | Inbox пользователя, включая постфильтр непрочитанных при необходимости |
| `inquiries_sent_idx` | senderId, createdAt DESC, id DESC | Sent пользователя |
| `moderation_target_idx` | targetUserId, createdAt DESC, id DESC | История конкретного участника и его последняя причина модерации |

Каталоги дополнительно проверяют статус/роль связанного User через join/relation predicate. Индекс на Asset не может сам гарантировать, что Seller ACTIVE. Предикат доступа применяется и в count, и в details, и при обращении.

Уникальные ограничения, создающие собственные индексы:

| Ограничение | Назначение |
| --- | --- |
| 5 PK, включая `buyer_profiles.user_id` | Идентичность, direct lookup, referenced side FK |
| `users_email_key` | Один нормализованный email; email перед записью trim/lowercase, CHECK поддерживает каноническое хранение |
| `inquiries_sender_request_key` на senderId + idempotencyKey | Одна запись на попытку отправки данного участника; одинаковый ключ другого отправителя допустим |

Всего 13 физических индексов после создания: 5 PK + 2 UNIQUE + 6 обычных. Новые CHECK-ограничения не добавляют индексов.

### Что намеренно не индексировано

- Отдельные sellerId, senderId, recipientId, targetUserId: уже первые поля составных индексов. userId профиля — уже PK; email — уже UNIQUE.
- role/status/country пользователя: основной доступ к пользователю по PK; небольшая модераторская таблица не требует набора индексов на каждый фильтр.
- category/country/license/status по одному: низкая селективность и произвольные сочетания; нет измеренной необходимости.
- price и budget: optional-сортировки и диапазонные фильтры пока выполняются на небольшой выдаче. Индекс на price не ускорит автоматически все сочетания фильтров и обе сортировки с NULLS LAST.
- GIN на два массива: всего несколько Buyer; стоимость и дополнительные структуры сейчас не оправданы. При росте проверить EXPLAIN для has/overlap и комбинации «пустой массив ИЛИ содержит страну».
- title/description/thesis обычным B-tree: поиск contains/ILIKE '%text%' им не решается. При росте отдельно рассмотреть pg_trgm и фактический план запроса; сейчас расширение не подключается.
- Inquiry.assetId и ModerationEvent.managerId: нет списка обращений по активу или истории по автору; физические удаления не рабочий сценарий. FK не требует автоматически отдельного индекса на referencing side.
- updatedAt: такой сортировки в принятом сценарии нет.
- Индекс для непрочитанных и partial indexes: отдельный unread-only каталог не требуется; предварительно добавлять partial-index preview feature Prisma не нужно.
- Огромный индекс из всех полей фильтров: несовместим с произвольным порядком условий и сортировок, увеличивает стоимость записи.

Уникальный индекс заявок с первым полем senderId НЕ заменяет `inquiries_sent_idx`: он не поддерживает порядок по времени. Это осмысленное пересечение, а не случайный дубликат.

## 6. Что защищает база, а что — use cases

`constraints.sql` содержит проверяемые внутри строки инварианты. Его нужно включить в миграцию; одной Prisma-схемы недостаточно для перечисленных ниже CHECK-гарантий. PostgreSQL считает CHECK успешным при TRUE или NULL, поэтому обязательность nullable-полей при публикации и соответствие priceType сумме проверяются явно через IS NULL / IS NOT NULL.

| В БД | В серверной бизнес-логике |
| --- | --- |
| PK, unique email, уникальная попытка отправки | Сессия, роль, ACTIVE, владение и видимость |
| FK, запрет самоконтакта/самомодерации | Противоположные роли отправителя/получателя; Buyer отправляет по активу; Seller прикрепляет только свой |
| Положительная фиксированная цена, отсутствие цены при ON_REQUEST | Корректный ввод не более двух десятичных знаков, форматирование EUR |
| Неотрицательные бюджеты и min <= max | Семантика фильтрации с отсутствующими границами |
| Поля опубликованного актива заполнены; дата соответствует lifecycle | Разрешённые переходы состояний, выставление/очистка дат |
| У публичного Buyer есть тезис и категории | Полнота связанных User.name/companyName/countryCode; заполненный профиль перед обращением |
| Непустой текст/причина и максимальные длины | Trim, понятные ошибки и отсутствие исполняемого HTML в UI |
| Допустимая пара fromStatus/toStatus | Один статусный переход и одно событие в одной транзакции |
| Массивы не NULL и без NULL-элементов | Allowlist стран и deduplicate интересов |

Роль участника или его ACTIVE-статус не проверяются через CHECK с чтением другой таблицы. Это не надёжный механизм cross-table constraints. Триггеры для бизнес-правил не добавляются.

Проверки длины обязательного текста удаляют POSIX whitespace по краям через `regexp_replace`, чтобы табуляции и переводы строк не заменяли содержательный ввод. Переносы внутри сообщения допустимы. Email дополнительно запрещает POSIX whitespace в любой позиции. Это базовая защита БД: Unicode trim/нормализация, полный синтаксис email и пользовательские сообщения об ошибках остаются в серверной валидации; идентичность всех правил SQL и JavaScript не предполагается.

`Decimal(18,2)` — предел хранения, не рыночный порог цены. Значения NaN запрещены CHECK-ограничениями. PostgreSQL может округлять ввод с большей точностью при приведении к numeric(18,2), поэтому запрет лишних десятичных знаков остаётся в Zod до записи. В JSON/API деньги передаются строками, а не преобразуются бездумно через JavaScript Number.

Даты — timestamptz(3), UTC на границе API. `@updatedAt` обслуживается Prisma Client, не триггером БД. Raw SQL обязан обновить его явно. Для readAt нужно использовать согласованные серверные/DB timestamps, значение не может быть раньше createdAt.

## 7. Атомарность и идемпотентность

1. Сохранение полей User и BuyerProfile — транзакция. Одновременные попытки создать профиль защищены его PK; использовать upsert по userId.
2. Публикация актива обновляет поля, status и publishedAt одним изменением после валидации. Редактирование PUBLISHED не должно временно записывать неполный объект.
3. Модерация в транзакции условно обновляет User по id и ожидаемому текущему status. Только если изменена одна строка, добавляет ModerationEvent. Повтор того же действия/конфликт не создаёт событие без перехода. Ошибка вставки события откатывает изменение User.
4. Обращение создаётся с ключом попытки. При unique conflict операция получает существующую запись, сравнивает неизменяемое нормализованное содержимое и возвращает её только для того же запроса. Тот же ключ с другими данными — конфликт. В PostgreSQL после ошибки внутри транзакции нельзя продолжать запросы в уже aborted transaction; чтение существующей записи выполняется после rollback/вне неё или используется корректный INSERT ON CONFLICT.
5. Idempotency key остаётся тем же при сетевом retry; новая осознанная заявка имеет новый ключ. Не вводить UNIQUE(senderId, recipientId, assetId): он ошибочно запретит повторные самостоятельные обращения и плохо выражает nullable assetId.

Доступность связанного пользователя/актива проверяется при новой отправке. Повтор уже сохранённого обращения рассматривается как повтор операции, а не новая доставка; текущий отправитель всё равно должен быть авторизован. При отсутствии текущей видимости карточка актива в истории не раскрывается.

Обычная транзакция сама по себе не устраняет гонку между проверкой ACTIVE/публикации и параллельной блокировкой/архивацией. Согласно scope, следующий запрос после завершённой модерации должен видеть актуальный статус, но глобальный порядок уже начавшихся конкурентных операций не обещается. Поэтому в MVP нужны свежие серверные проверки без общего кэша авторизации; усложнять модель дополнительными таблицами блокировок или версиями всех сущностей не требуется.

## 8. Seed и интеграция на следующем шаге

Fixtures: 13 пользователей (8 Buyer, 4 Seller, 1 Manager), 7 BuyerProfile, 20 активов, 5 обращений и 2 события модерации. Один Buyer без профиля, один с неполным черновиком, один заблокирован; один Seller заблокирован. Есть опубликованный актив заблокированного продавца, старое обращение с ним, черновики, архивные активы и ON_REQUEST.

Файл содержит `demoPersonas` для allowlist выбора аккаунтов; это конфигурация seed, не новая таблица и не user-controlled флаг в БД. Для тестов доступны две пары Buyer/Seller. Статусы заблокированных участников согласованы с событиями модерации.

Будущий seed-скрипт: загрузить JSON, преобразовать decimal-строки и даты, создать записи в порядке users → buyerProfiles/assets → inquiries/moderationEvents. Использовать стабильные ключи и пропуск существующих записей; не upsert-обновлять пользовательские изменения при обычном запуске. Повторная проверка конфликтов должна сообщать проблему, а не молча переназначать ссылки. `reset-demo` — отдельная явная команда для демонстрационной БД.

На шаге 3:

1. Установить согласованные версии Prisma CLI, client и adapter-pg; настроить prisma.config.ts с DATABASE_URL, путями и seed-командой.
2. Запустить локальный PostgreSQL в Docker; задать отдельную test DB.
3. Создать initial migration через `prisma migrate dev --create-only --name init`.
4. Добавить содержимое constraints.sql после generated DDL. Не применять этот файл отдельно повторно после каждого запуска и не использовать db push как замену миграциям.
5. Применить миграцию, сгенерировать клиент, реализовать и запустить seed, проверить повторный seed и перезапуск контейнеров.
6. Проверить SQL-инварианты на настоящем PostgreSQL и сервисные правила тестами. Изменения CHECK впоследствии оформляются отдельными SQL-миграциями; они не описаны нативными Prisma model attributes.

## 9. Статус проверки

- `prisma format` и `prisma validate` выполнены успешно с Prisma CLI 7.10.0.
- `prisma migrate diff --from-empty --to-schema ... --script` с временным Prisma config сгенерировал DDL без обращения к рабочей БД.
- Полученный DDL и constraints.sql успешно выполнены в изолированном PGlite, использующем PostgreSQL 17.5 в WebAssembly. Это проверка SQL, не запуск PostgreSQL-контейнера приложения.
- Все подготовленные fixtures загружены. Отдельно проверены соответствие ролей/владения, количество таблиц/индексов/FK/CHECK и результаты каталогов с блокировками.
- Всего прошли 39 проверок: среди них дубли профиля/email/попытки отправки, новый самостоятельный контакт с тем же участником, отрицательные и обратные бюджеты, NaN, неполная публикация, NULL в ценовых условиях и массивах, внешние ключи, ограничение удаления, неверный переход модерации и откат транзакции при невалидном audit event.
- В процессе проверки явно закрыт SQL NULL-case: цена без priceType должна отклоняться, а не проходить CHECK через UNKNOWN. Также Prisma-generated arrays дополнены NOT NULL в SQL, поскольку одного list-поля модели недостаточно для этой гарантии на уровне БД.
- Повторное ревью воспроизвело 10 недопустимых записей, которые проходили старые CHECK: обязательные поля из табуляций/переводов строк, короткий заголовок с такой отбивкой и email с пробельными символами. После исправления все 10 отклоняются. Два положительных сценария — многострочное сообщение и имя на кириллице — остаются допустимыми.
- После исправления повторно прошли исходные 39 проверок и 12 дополнительных, всего 51. Число таблиц, индексов, FK и CHECK не изменилось.

Не проверялись производительность на большой выборке, планы EXPLAIN, Docker networking, авторизация/HTTP-операции и runtime seed-скрипт: этих частей приложения ещё нет. Успех этих SQL-проверок не заменяет интеграционную приёмку после запуска Docker. На этом этапе не применялась миграция пользовательской БД и не выполнялся деплой.

## 10. Итог повторного ревью и обязательства реализации

Лишних таблиц в выбранном scope не обнаружено. Четыре таблицы обслуживают основные сценарии; пятая, `moderation_events`, сохраняет уже согласованную историю причин модерации. Отдельные роли, продавцы, организации, чаты, уведомления и таблицы интересов пока не нужны. Шесть обычных индексов соответствуют конкретным путям чтения; это обоснованный начальный набор, а не измеренная гарантия производительности на большой БД.

| Место возможной ошибки | Что необходимо при реализации |
| --- | --- |
| FK подтверждает пользователя, но не его роль | Сервер проверяет роль, ACTIVE и владение; role нельзя менять через редактирование профиля |
| Публичный Buyer связан с редактируемым User | Любое изменение общего имени/компании/страны сохраняет полноту опубликованного профиля; User и BuyerProfile валидируются совместно |
| Заблокированный Seller остаётся владельцем PUBLISHED-активов | Одинаковое условие видимости в каталоге, count, details и новой отправке; доступ активной стороны к старым обращениям сохраняется |
| Повтор заявки с тем же ключом, но другим текстом | Unique предотвращает вторую запись; use case сверяет нормализованный payload и возвращает конфликт, а не успех чужого содержимого |
| Статус пользователя и запись аудита могут разойтись | Условное обновление статуса и вставка события выполняются одной транзакцией; ошибка откатывает оба действия |
| Одной Prisma-схемы недостаточно для CHECK | constraints.sql включается в initial migration; дальнейшие изменения ограничений — отдельные SQL-миграции, без db push вместо миграций |

Пункты таблицы — обязанности будущего приложения, а не уже реализованные гарантии. На шаге 3 необходимо подтвердить миграции и сохранение данных на PostgreSQL в Docker; сервисные проверки подтвердить по мере реализации соответствующих use cases.
